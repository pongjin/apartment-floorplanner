# 커밋 작업 기록 작성 지침

## 목적

코드만으로 파악하기 어려운 작업 배경, 판단 근거, 검증 결과와 배포 상태를 커밋과 함께 남깁니다. 기록은 다음 작업자가 같은 조사와 시행착오를 반복하지 않도록 하는 데 목적이 있습니다.

## 적용 범위

다음 커밋에는 작업 기록을 반드시 포함합니다.

- 기능 추가와 동작 변경
- 버그 수정과 성능 개선
- 데이터 구조·의존성·빌드 설정 변경
- UI·접근성·반응형 레이아웃 변경
- 배포·운영·보안·개인정보 처리 변경
- 사용자 또는 개발자용 문서의 의미 있는 변경

오탈자 한 글자 수정처럼 설명 가치가 없는 변경은 기존 기록의 비고에 합칠 수 있습니다.

## 파일 규칙

- 위치: `work_dir/`
- 이름: `YYYY-MM-DD-영문-작업명.md`
- 한 커밋에 하나의 주제가 원칙이며, 강하게 연결된 변경은 하나의 기록으로 묶습니다.
- 비밀번호, 토큰, 개인 도면, 사용자 개인정보, 로컬 전용 경로는 기록하지 않습니다.
- 커밋 생성 전에는 SHA를 알 수 없으므로 `관련 커밋: 이 기록을 포함하는 커밋`이라고 작성합니다.
- 이미 완료된 커밋을 소급 정리할 때만 `관련 커밋: <short SHA>`를 사용합니다.

## 필수 항목

각 기록에는 아래 항목을 순서대로 작성합니다.

1. 관련 커밋과 커밋 제목
2. 작업 배경과 목표
3. 변경 내용
4. 사용자 경험 또는 데이터 영향
5. 검증 방법과 결과
6. 배포 여부
7. 남은 한계와 후속 작업

## 커밋 전 체크리스트

```text
[ ] 변경 범위에 맞는 테스트와 빌드를 실행했다.
[ ] work_dir에 이번 작업 기록을 생성하거나 갱신했다.
[ ] work_dir/INDEX.md에 기록 링크를 추가했다.
[ ] 실제 검증 결과와 알려진 한계를 기록했다.
[ ] 비밀값·개인정보·불필요한 생성 파일이 포함되지 않았다.
[ ] git diff --check와 git status를 확인했다.
```

## 권장 템플릿

```markdown
# 작업 제목

- 날짜: YYYY-MM-DD
- 관련 커밋: 이 기록을 포함하는 커밋
- 커밋 제목: `type: concise summary`

## 배경과 목표

왜 이 작업이 필요한지 작성합니다.

## 변경 내용

- 핵심 변경 1
- 핵심 변경 2

## 영향

사용자 흐름, 저장 데이터, 호환성 또는 운영 영향이 있으면 작성합니다.

## 검증

- 실행한 명령
- 브라우저·기기 조건
- 성공 및 실패 케이스 결과

## 배포

push와 배포 상태를 작성합니다.

## 남은 한계

다음 작업자가 알아야 할 제약과 후속 작업을 작성합니다.
```

## 커밋 절차

```bash
pnpm build
git diff --check
git status
git add <변경 파일> work_dir/<기록 파일>.md work_dir/INDEX.md
git commit -m "<type>: <summary>"
git push origin main
```

`main` push는 Vercel Production 자동 배포를 시작하므로 기능 커밋은 배포 가능한 상태에서만 push합니다.
