# 자동인식 고도화 검토

최종 갱신: 2026-08-30

## 결론

OpenCV는 현재 가장 약한 **도면 본체 분리, 끊어진 벽 연결, 벽 선분과 개구부 후보 생성**을 개선하는 데 적합합니다. 반면 문과 창의 의미를 다양한 도면 양식에서 안정적으로 구분하는 문제는 OpenCV만으로 해결하기 어렵습니다. 따라서 `OpenCV 후보 생성 + 경량 문·창 분류 모델 + 기존 벡터 후처리`의 혼합 구성을 권장합니다.

현재 두 회귀 도면만으로 정확도 향상률을 확정할 수는 없습니다. 아래 수치는 공식 기능과 공개 데이터셋 규모, 현재 오류 유형을 바탕으로 한 개발 계획용 추정치이며, 최소 100개 평가 도면에서 별도로 검증해야 합니다.

## 현재 휴리스틱의 관찰 결과

| 도면 | 수정 전 | 수정 후 | 관찰 |
| --- | --- | --- | --- |
| `sample_map.png` | 벽 18·문 3·창 0, 창이 미닫이문 후보 | 벽 17·일반문 2·창 1 | 업로드 통과, 미닫이문 회귀 해소 |
| 대형 회귀 도면 | 벽 21·문 1·창 2, 상단 구조 누락 | 벽 26·일반문 2·창 0 | 상단 복원, 눈으로 보이는 일반문 약 5개 중 2개 검출 |

남은 주된 오류는 분류기가 아니라 개구부 **후보 생성 누락**입니다. 현재 방식은 같은 축의 두 벽 선분 사이에 적정 크기의 틈이 있을 때만 후보를 만듭니다. 문 열림 호나 벽선이 흐리거나 다른 기호와 겹치면 분류 단계까지 도달하지 않습니다.

## OpenCV 적용 시 기대 효과

OpenCV의 형태학적 closing은 작은 단절을 연결하고, opening은 가는 잡음을 제거할 수 있습니다. `HoughLinesP`는 조금 끊기거나 왜곡된 선도 검출할 수 있으며, 연결요소 통계는 도곽·텍스트·작은 아이콘을 면적과 종횡비로 거르는 데 사용할 수 있습니다. 원호는 전체 원 검출보다 벽 끝점 주변의 제한된 반경에서 contour와 호 일치도를 계산하는 편이 문 기호에 적합합니다.

공식 참고 자료:

- [OpenCV 형태학 연산](https://docs.opencv.org/4.13.0/d9/d61/tutorial_py_morphological_ops.html)
- [OpenCV Hough Line Transform](https://docs.opencv.org/4.x/d9/db0/tutorial_hough_lines.html)
- [OpenCV 연결요소 및 형태 분석](https://docs.opencv.org/doc/doxygen/html/d3/dc0/group__imgproc__shape.html)
- [OpenCV.js 브라우저 사용법](https://docs.opencv.org/5.0/js_tutorials/js_setup/js_usage/js_usage.html)

예상 범위:

- 벽·개구부 후보 재현율: 현재 대상 양식에서 약 10~25%p 개선 가능성이 있습니다.
- 벽 선분 파편화: morphology와 Hough 병합으로 약 20~40% 감소할 가능성이 있습니다.
- 문·창 의미 분류: OpenCV만 추가하면 약 0~10%p 수준의 제한적인 개선을 예상합니다.
- 처리 속도: 정확도는 좋아질 수 있지만 OpenCV.js 초기 로드와 WASM 메모리 비용 때문에 첫 실행은 느려질 수 있습니다. 분석을 Web Worker에서 수행하고 긴 변을 분석 전용 최대 해상도로 제한해야 UI 멈춤을 피할 수 있습니다.

이 수치는 보장값이 아닙니다. `IMG_2688`에서 누락된 문 3개를 전부 복원할 수 있는지는 형태학 커널과 후보 결합 규칙을 적용한 뒤 실제 정답 라벨로 측정해야 합니다.

## 권장 구현 순서

1. 원본을 분석용 1,200~1,600px 긴 변으로 정규화하고 적응형 threshold를 적용합니다.
2. 수평·수직 morphology closing으로 끊어진 벽을 연결하고 opening으로 텍스트와 잔선을 줄입니다.
3. 연결요소 통계로 작은 텍스트와 하단 도곽을 제거합니다.
4. `HoughLinesP` 결과를 각도·거리·두께로 묶어 벽 중심선을 만듭니다.
5. 벽의 틈뿐 아니라 벽 끝점 주변 contour에서도 개구부 후보를 생성합니다.
6. 벽 끝점에 붙은 1/4 원호와 방사형 문짝 선을 점수화합니다.
7. 자동 후보는 일반문과 창만 출력하고, 낮은 신뢰도 후보는 숨기거나 사용자의 확인 대상으로 둡니다.
8. OpenCV.js는 자동 인식 시점에만 lazy load하고 Web Worker에서 실행합니다.

## 라벨링 데이터 규모

OpenCV 자체는 학습하지 않으므로 학습 라벨이 필요하지 않습니다. 하지만 개선 여부를 객관적으로 측정할 평가 데이터는 반드시 필요합니다.

| 단계 | 권장 도면 수 | 권장 인스턴스 수 | 목적 |
| --- | ---: | ---: | --- |
| OpenCV 휴리스틱 평가 | 100~200 | 문·창 1,000개 이상 | 양식별 precision/recall과 처리 시간 확정 |
| 전이학습 PoC | 300~500 | 문·창 3,000~8,000 | 일반문/창 분류 가능성 및 실패 양식 확인 |
| 국내 도면 프로덕션 | 1,500~3,000 | 문·창 15,000~30,000 | 공급처·색상·해상도·기호 차이에 대한 안정화 |
| 전체 구조 dense segmentation | 3,000~5,000 이상 | 벽·방 polygon 포함 | 방·벽·개구부를 함께 벡터화하는 모델 |

라벨은 픽셀 마스크보다 `부모 벽 ID + 양 끝점 + 유형(일반문/창)` 형식이 이 앱의 데이터 모델과 잘 맞고 작성 비용도 낮습니다. 미닫이문과 베란다문은 자동 인식 대상이 아니므로 `ignore` 영역으로만 표시합니다.

공개 기준으로 [CubiCasa5K](https://github.com/CubiCasa/CubiCasa5k)는 5,000개 도면과 80개 이상의 polygon 범주를 제공하며, 공개 논문도 동일 규모를 설명합니다. [FloorNet](https://openaccess.thecvf.com/content_ECCV_2018/html/Chen_Liu_FloorNet_A_Unified_ECCV_2018_paper.html)은 155개 주거 공간 전체 라벨을 사용한 연구용 벤치마크 사례입니다. 이 숫자들은 좁은 PoC는 수백 장으로 시작할 수 있지만 다양한 실제 양식의 제품 안정성에는 수천 장이 필요하다는 규모 참고치입니다. 공개 데이터는 국내 부동산 도면 기호와 다를 수 있고 사용 전 현재 라이선스를 별도로 확인해야 합니다.

## 평가 설계

- 도면 공급처와 스타일 단위로 train/validation/test를 분리해 거의 같은 변형 이미지가 서로 다른 집합에 섞이지 않게 합니다.
- 벽은 선분 endpoint 허용오차와 길이 IoU, 문·창은 부모 벽과 두 endpoint 허용오차로 평가합니다.
- 최소 지표는 벽 precision/recall, 일반문 precision/recall, 창 precision/recall, 도면당 처리 시간, 모바일 peak memory입니다.
- 초기 300장을 라벨링한 뒤 모델의 낮은 신뢰도와 오탐 사례를 100~200장 단위로 추가하는 active learning 방식을 권장합니다.
- 현재 회귀 도면 두 개는 고정 fixture로 두되, 전체 성능 수치에는 포함하지 않고 회귀 통과 여부만 확인합니다.
# 현재 적용 상태 — 2026-08-31

로드맵의 전이학습 PoC를 제품에 적용했다. 현재 기본 자동 인식은 휴리스틱 벽 그래프와 AI Hub STR 1,500장 전이학습 LRASPP 문·창 분할 모델을 결합한다. 모델은 ONNX Runtime Web WASM으로 브라우저에서 실행되며 사용자 이미지는 서버로 전송하지 않는다.

- 제품 벽: 기존 TypeScript 휴리스틱을 유지하고 모서리·직선 연속성을 담당
- 제품 문: AI 후보를 실제 유한 벽 선분까지의 2차원 거리로 부착
- 제품 창: 긴 형상 방향을 유지해 같은 방향 벽 축과 의도적인 벽 틈에 부착
- 오탐 억제: 벽 범위 밖, 벽에서 먼 후보, 짧은 고립 창, 낮은 확률 코너 창 제거
- 자동 클래스: 여닫이문, 미닫이문, 기타문, 여닫이창, 미닫이창, 기타창
- 레거시: `src/legacy/floorPlanDetectionHeuristic.ts`

검증 모델의 validation mean IoU는 0.4198이다. 이 값은 전체 픽셀 분할 지표이며 실제 서비스 도면의 객체 단위 정확도와 같지 않다. 제품 배포 후에는 사용자 수정 이력을 익명 집계하지 않으므로, 고정 정답 fixture를 별도로 구축해 객체 precision/recall을 측정해야 한다.
